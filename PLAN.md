# ГЭСН-поиск: план проекта

Поиск кода работы ГЭСН по описанию в свободной форме. Сравниваем лексический поиск, готовую модель эмбеддингов и модель, дообученную на доменных парах.

Срок: 2–3 недели при частичной занятости (~12–15 ч/нед). Бюджет: 0 ₽. Железо: Ryzen 5 5500 (CPU) + бесплатные GPU Kaggle/Colab.

---

## Ограничения и как их обходим

| Ограничение | Решение |
|---|---|
| Нет экспертизы в сметах | Тест пишется с позиции заказчика-неспециалиста — это и есть целевой пользователь. Разметку правильных кодов делает LLM-судья (Claude Code) с выборочной проверкой человеком |
| Нет GPU | Kaggle Notebooks (бесплатно ~30 ч GPU в неделю) для генерации синтетики и файнтюна. Локально на CPU — BM25, инференс, демо |
| Нулевой бюджет на API | Синтетику генерирует открытая instruct-модель на 7–8B (семейство Qwen или аналог, актуальная на момент старта) через vLLM на Kaggle. Запасные варианты: бесплатные лимиты API или Ollama на CPU на ночь |

**Защита от утечки:** обучающие запросы генерирует открытая модель, а тест пишет человек, размечает Claude. Разные семейства моделей, разные источники текста.

## Данные

**Справочник:** ФСНБ-2022 в XML, официально опубликована на ФГИС ЦС: https://fgiscs.minstroyrf.ru/frsn/fsnb (сайт на JS, скачивать руками через браузер).

**Скоуп (зафиксирован):** 6 сборников ГЭСН с «бытовыми» работами — 2940 норм, 625 таблиц. Сборник 01 (земляные работы) исключён: 2324 нормы, в основном экскаваторы разных типов.
- 06 Бетонные и ж/б конструкции монолитные — 756
- 08 Конструкции из кирпича и блоков — 310
- 10 Деревянные конструкции — 467
- 11 Полы — 215
- 12 Кровли — 176
- 15 Отделочные работы — 1016

MVP: только 11 + 15 (~1230 норм).

**Единица документа:** норма = `код` + `название таблицы` + `уточнение нормы` + `единица измерения`. Таблица (`06-01-001`) — второй уровень оценки.

**Обучающие пары:**
- 3–5 запросов на норму в разных регистрах: прораб, заказчик, коротко/обрывочно, с опечатками, без единиц измерения → ~10–20 тыс. пар.
- Hard negatives: соседние нормы из той же таблицы (отличаются параметром) и нормы из соседних таблиц.
- Фильтр качества: убрать дубли и запросы, которые дословно копируют название нормы (иначе модель учится копированию).

## Оценка

**Тест A (основной, ~150 запросов, ручной):**
1. Автор смотрит только названия сборников и разделов, но не тексты норм, и пишет запросы «как заказчик»: «поменять стяжку в ванной», «залить фундамент под баню».
2. Пулинг: top-10 от каждого метода (BM25, e5, гибрид) → объединение кандидатов.
3. Claude Code размечает релевантность каждого кандидата: точный код / правильная таблица / мимо. Автор выборочно проверяет ~20%.
4. Тест **замораживается до файнтюна**. Новые кандидаты от дообученной модели доразмечаются тем же способом, неразмеченные считаются нерелевантными (стандартная практика TREC — описать в README).

**Тест B (вспомогательный):** синтетика с другим промптом на отложенных нормах — только для отладки, в итоговую таблицу идёт отдельной строкой.

**Тест C (stretch):** реальные пары «ведомость объёмов работ ↔ локальная смета» из документации госзакупок.

**Метрики** на двух уровнях (точный код и таблица): Recall@1/5/10, MRR@10, бутстреп-доверительный интервал 95%.

## Подходы

1. **BM25** — `bm25s` + лемматизация `pymorphy3`.
2. **Готовая модель** — `intfloat/multilingual-e5-base` (префиксы `query:` / `passage:`). Опционально `deepvk/USER-base` для сравнения.
3. **Дообученная модель** — e5-base + `MultipleNegativesRankingLoss` (in-batch negatives + hard negatives), `sentence-transformers` 3.x, 1–3 эпохи на Kaggle T4.
4. **Гибрид** — BM25 + лучшая dense-модель через Reciprocal Rank Fusion.

Индекс — numpy с косинусной близостью (5 тыс. документов, FAISS не нужен).

## Этапы

| # | Этап | Готово, когда |
|---|---|---|
| 0 | Скачать XML, разобрать структуру | Понятна схема XML, выбраны сборники |
| 1 | Парсер → `norms.parquet` | Таблица `code, table_code, table_name, norm_name, unit` на 3–5 тыс. строк |
| 2 | Ручной тест: запросы | 150 запросов в `test_queries.csv` |
| 3 | BM25 + e5 zero-shot + обвязка для оценки | `evaluate.py` выдаёт таблицу метрик для любого retriever'а |
| 4 | Пулинг и разметка теста | Тест A заморожен, baseline-цифры зафиксированы |
| 5 | Генерация синтетики на Kaggle | `train_pairs.jsonl`, 10–20 тыс. пар, отфильтрованы |
| 6 | Файнтюн на Kaggle | Модель сохранена, цифры на тесте A |
| 7 | Гибрид + разбор ошибок | 5–10 разобранных провалов на каждый подход |
| 8 | Упаковка | README с таблицей, FastAPI `/search`, CLI, модель на HF Hub |

**Неделя 1:** этапы 0–3. **Неделя 2:** 4–6. **Неделя 3:** 7–8.

## MVP на крайний случай (~20–25 ч)

- 2 сборника (~1–1,5 тыс. норм)
- 80–100 тестовых запросов
- BM25 vs e5 vs дообученная e5
- CLI + README с таблицей

Вне MVP: гибрид, тест C, FastAPI, HF Hub, Gradio.

## О чём говорить на собеседовании

- Почему MNRL, а не triplet loss; откуда берутся hard negatives.
- Как устроен тест без утечки: разные источники для обучения и теста, заморозка до файнтюна, пулинг.
- Где эмбеддинги проигрывают BM25 (числа, параметры) и зачем нужен гибрид.
- Доверительные интервалы: какая разница между подходами значимая, а какая — шум.
